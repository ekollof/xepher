       Introduction<a class="anchor-link" href="#intro"><abbr title="Link to this point in the document">¶</abbr></a></h2>
  <p class="" style=""><span class="ref" style=""><a href="http://tools.ietf.org/html/rfc6120">XMPP Core</a></span>  [<a href="#nt-idm44867749053872">1</a>] allows XMPP server implementations to support any SASL mechanism (see <span class="ref" style=""><a href="http://tools.ietf.org/html/rfc4422">RFC 4422</a></span>  [<a href="#nt-idm44867749049648">2</a>]) when authenticating clients. This document provides recommendations regarding use of the SASL ANONYMOUS mechanism (see <span class="ref" style=""><a href="http://tools.ietf.org/html/rfc4505">RFC 4505</a></span>  [<a href="#nt-idm44867749040464">3</a>]) in XMPP systems.</p>
<h2 id="deployments">2.
       Deployment Types<a class="anchor-link" href="#deployments"><abbr title="Link to this point in the document">¶</abbr></a></h2>
  <p class="" style="">XMPP server implementations can be deployed in a variety of settings. Although it is difficult to provide recommendations for every kind of XMPP deployment, this document attempts to strike a balance between more and less controlled settings by defining three different deployment types:</p>
  <ul class="" style="">
    <li class="" style="">Public deployments, such as well-known instant messaging (IM) services on the open Internet.</li>
    <li class="" style="">Private deployments, such as enterprise IM services, technical support departments, and helplines.</li>
    <li class="" style="">Specialized deployments that typically will be accessed in a controlled fashion, such as gaming services, members-only websites, and applications that are not used directly by human users.</li>
  </ul>
<h2 id="recommendations">3.
       Recommendations<a class="anchor-link" href="#recommendations"><abbr title="Link to this point in the document">¶</abbr></a></h2>
  <p class="" style="">An XMPP server implementation SHOULD NOT enable the SASL ANONYMOUS mechanism by default, but instead SHOULD force the administrator of a given service to explicitly enable support in the context of that deployment.</p>
  <p class="" style="">When a client authenticates using SASL ANONYMOUS, an XMPP server SHOULD assign a temporary, unique bare JID &lt;localpart@domain.tld&gt; to the client. Although the method for ensuring the uniqueness of the localpart is a matter of implementation, it is RECOMMENDED for the localpart to be a UUID as specified in <span class="ref" style=""><a href="http://tools.ietf.org/html/rfc4122">RFC 4122</a></span>  [<a href="#nt-idm44867749030528">4</a>].</p>
  <p class="" style="">Although <span class="ref" style=""><a href="http://tools.ietf.org/html/rfc4505">RFC 4505</a></span>  [<a href="#nt-idm44867749040464">3</a>] allows the client to provide so-called "trace data" when authenticating via SASL ANONYMOUS, it is NOT RECOMMENDED for the client to include trace data as the XML character data of the &lt;auth/&gt; element (instead, the &lt;auth/&gt; element SHOULD be empty). However, if trace data is included, the server MUST NOT use it for any purpose other than tracing (e.g., not use it as the resource identifier of the anonymous user's full JID).</p>
  <p class="" style="">Because an anonymous user is unknown to the server, the server SHOULD appropriately restrict the user's access in order to limit the possibility of malicious behavior (such as denial of service attacks as described in <span class="ref" style=""><a href="https://xmpp.org/extensions/xep-0205.html">Best Practices to Discourage Denial of Service Attacks (XEP-0205)</a></span>  [<a href="#nt-idm44867749021168">5</a>]), especially on public deployments. The following restrictions are encouraged on public deployments. Administrators of private deployments and specialized deployments are advised to take these restrictions into account when configuring their services, but can reasonably relax these restrictions if they have appropriate access controls in place or their deployment requirements cannot be met using the more restrictive profile applied in public deployments.</p>
  <ol start="1" class="" style="">
    <li class="" style=""><p class="" style="">During resource binding, the server MAY ignore the resource identifier provided by the client (if any) and instead assign a resource identifier that it generates on behalf of the client.</p></li>
    <li class="" style=""><p class="" style="">The server SHOULD NOT allow the client to initiate communication with entities hosted at remote servers.</p></li>
    <li class="" style=""><p class="" style="">The server MAY allow the client to establish relationships with local services and users; such relationships might include presence subscriptions and roster additions (see <span class="ref" style=""><a href="http://tools.ietf.org/html/rfc6121">XMPP IM</a></span>  [<a href="#nt-idm44867749009392">6</a>]), <span class="ref" style=""><a href="https://xmpp.org/extensions/xep-0045.html">Multi-User Chat (XEP-0045)</a></span>  [<a href="#nt-idm44867749004976">7</a>] registrations, and <span class="ref" style=""><a href="https://xmpp.org/extensions/xep-0060.html">Publish-Subscribe (XEP-0060)</a></span>  [<a href="#nt-idm44867748996064">8</a>] subscriptions. (Note that allowing presence subscriptions and roster additions can create a sub-optimal user experience for the added contacts.) However, if the server permits such relationships, it MUST cancel them when the client's session ends.</p></li>
    <li class="" style=""><p class="" style="">The server MAY allow the client to store information on the server for the purpsoe of providing an optimal user experience (e.g., storage of client preferences using <span class="ref" style=""><a href="https://xmpp.org/extensions/xep-0049.html">Private XML Storage (XEP-0049)</a></span>  [<a href="#nt-idm44867748993328">9</a>]). However, if the server allows this, it SHOULD remove such information when the client's session ends.</p></li>
    <li class="" style=""><p class="" style="">The server SHOULD NOT allow the client to send large numbers of XMPP stanzas or otherwise use large amounts of system resources (e.g., by binding multiple resource identifiers or creating multiple <span class="ref" style=""><a href="https://xmpp.org/extensions/xep-0065.html">SOCKS5 Bytestreams (XEP-0065)</a></span>  [<a href="#nt-idm44867748987184">10</a>] sessions).</p></li>
  </ol>
<h2 id="flow">4.
       Protocol Flow<a class="anchor-link" href="#flow"><abbr title="Link to this point in the document">¶</abbr></a></h2>
  <p class="" style="">The RECOMMENDED protocol flow following TLS negotiation (refer to <span class="ref" style=""><a href="http://tools.ietf.org/html/rfc3920">RFC 3920</a></span>  [<a href="#nt-idm44867748982032">11</a>]) is as follows:</p>
  <ol start="" class="" style="">
    <li class="" style="">
      <p class="" style="">Client initiates stream to server.</p>

&lt;stream:stream
        xmlns:stream='http://etherx.jabber.org/streams'

        to='example.com'
        version='1.0'&gt;
</pre></figure>
    </li>
    <li class="" style="">
      <p class="" style="">Server replies with stream header.</p>
      <figure class="code-example" id="example-2"><figcaption><strong>Example 2.</strong> Stream header reply<a class="anchor-link" href="#example-2"><abbr title="Link to this point in the document">¶</abbr></a></figcaption><pre class="prettyprint">
&lt;stream:stream
        xmlns:stream='http://etherx.jabber.org/streams'

        id='c2s_234'
        from='example.com'
        version='1.0'&gt;
</pre></figure>
    </li>
    <li class="" style="">
      <p class="" style="">Server advertises stream features.</p>
      <figure class="code-example" id="example-3"><figcaption><strong>Example 3.</strong> Stream features advertisement<a class="anchor-link" href="#example-3"><abbr title="Link to this point in the document">¶</abbr></a></figcaption><pre class="prettyprint">

    <li class="" style="">
      <p class="" style="">Client opens new stream.</p>
      <figure class="code-example" id="example-6"><figcaption><strong>Example 6.</strong> Initiating a new stream<a class="anchor-link" href="#example-6"><abbr title="Link to this point in the document">¶</abbr></a></figcaption><pre class="prettyprint">

<h2 id="disco">5.
       Service Discovery<a class="anchor-link" href="#disco"><abbr title="Link to this point in the document">¶</abbr></a></h2>
  <p class="" style="">A server MUST reply to a <span class="ref" style=""><a href="https://xmpp.org/extensions/xep-0030.html">Service Discovery (XEP-0030)</a></span>  [<a href="#nt-idm44867748949808">12</a>] information ("disco#info") request sent to the bare JID &lt;localpart@domain.tld&gt; of the user with an identity of "account/anonymous", as shown in the following example.</p>
  <figure class="code-example" id="example-10"><figcaption><strong>Example 10.</strong> Server informs client of full JID<a class="anchor-link" href="#example-10"><abbr title="Link to this point in the document">¶</abbr></a></figcaption><pre class="prettyprint">
&lt;iq from='59BEC12A-9BAB-452B-88F8-D1563F09E549@example.com'
    id='kj37vd95'
    to='requester@example.com/foo'
    type='result'&gt;
  &lt;query xmlns='http://jabber.org/protocol/disco#info'&gt;
    &lt;identity category='account' type='anonymous'/&gt;
    &lt;feature var='http://jabber.org/protocol/disco#info'/&gt;
    &lt;feature var='http://jabber.org/protocol/disco#items'/&gt;
  &lt;/query&gt;
&lt;/iq&gt;
</pre></figure>
